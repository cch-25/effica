# 기사 보관 규칙

- 전체 `articles` 행 수는 상태와 분석 완료 여부에 관계없이 최대 300개다.
- 발행 시각과 최초 저장 시각 중 이른 시각으로부터 7일을 넘으면 삭제한다. 발행 시각이 없으면 최초 저장 시각을 사용한다. 미래 발행 시각으로 보관 기간을 연장할 수 없다.
- 날짜별 분류는 같은 기준 시각의 한국 날짜를 사용한다. 7일은 168시간이므로 양 끝의 일부 날짜를 포함해 달력 날짜가 8개일 수 있다.

먼저 만료 기사를 모두 삭제 대상으로 정한다. 현재 발행 중인 유효한 이슈의 기사는 우선 보존한다. 승인된 독립 언론사 3곳 이상과 현재 기사 버전이 있는 일일 큐레이션 이슈 최대 5개가 대상이다. 이슈당 최대 8개이므로 정상 발행 묶음은 최대 40개이며, 7일이 지난 기사에는 예외를 적용하지 않는다.

이후 남은 보관 공간에 이전 묶음과 기타 미만료 기사를 배분한다. 날짜별 보존 수는 `남은 공간 × 해당 날짜의 비보호 기사 수 / 전체 비보호 기사 수`로 계산한다. 소수점은 버린 후 남은 자리를 소수 부분이 큰 날짜부터 배분한다. 동률이면 최근 날짜가 우선이다. 보호할 현재 이슈가 없는 상태에서 7개 날짜에 각각 100개씩 있으면 6개 날짜는 43개, 나머지 날짜는 42개를 남긴다.

각 날짜의 보존 수 안에서는 출처별 선택 수가 적은 출처를 먼저 선택하고, 다음으로 선택 수가 적은 주제를 우선한다. 그 다음 기준은 AI 분석 완료 여부와 안정적인 기사 ID다. 날짜 비율은 유지하면서 가능한 범위에서 출처와 주제가 사라지지 않도록 한다. 그 날짜의 보존 수보다 출처 수가 많으면 모든 출처를 동시에 보존할 수는 없다.

수집 결과 저장과 정리는 `article_inventory_guard`의 같은 행을 트랜잭션 잠금으로 사용한다. 새 기사 저장 후 초과분을 제거하고 커밋하기 때문에 병렬 수집 중에도 외부 연결에 300개 초과 상태가 노출되지 않는다. 시드 입력도 같은 경계를 따른다.

`effica-article-expiry.service`는 수집이 없는 동안에도 1초마다 만료 여부를 검사한다. API는 저장소를 제공하기 전에 만료 여부를 재검사하므로 검사 프로세스가 중단됐더라도 요청 시 만료 기사를 정리한다. 실제 물리 삭제는 검사 트랜잭션 완료 시점에 이루어지며, 벽시계가 만료 시각을 통과한 바로 그 순간에 SQL 삭제가 완료된다는 뜻은 아니다.

읽기나 투표, 공유 기록이 있다는 이유로 기사 보관을 연장하지 않는다. 읽기와 투표 행은 기사 연결을 해제해 보존하며, 크레딧 원장은 변경하지 않는다. 삭제한 기사의 버전과 분석 결과, 관련 작업과 사용되지 않는 기사 본문 블롭을 제거한다. 삭제한 URL 해시는 재수집 방지용으로 보관한다. 사용자 공유 산출물과 내보내기 파일은 별도 사용자 데이터이며 기사 수에 포함하지 않는다.

AI의 하루 100개 한도는 별도의 분석 예산이다. 저장량 300개 제한을 이 예산에 의존하지 않는다. 정기 수집은 한국 날짜 기준 하루 한 번 이슈를 먼저 발굴한다. 이슈당 기사 3~5개가 기본이며 별도 쟁점 근거가 있는 경우에만 최대 8개까지 포함한다. 새 이슈와 아직 유효한 기존 이슈를 합해 최대 5개를 발행한다. 사용자 데이터 생성 작업은 기존 우선순위를 유지한다.

검증에는 날짜 비례 배분, 출처 보존, 만료 경계, 사용자 활동 보존, 삭제 후 재수집 차단을 포함한다. 별도 로컬 MariaDB에서 이전 스키마부터의 마이그레이션과 두 동시 수집 트랜잭션, 외부 관찰자의 300개 상한, 유휴 상태 만료 정리를 검증한다. 운영 DB를 테스트용으로 사용하지 않는다.
